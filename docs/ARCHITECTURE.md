# Calo — архитектура

Личный счётчик калорий и нутриентов с недельным разбором и рекомендациями.
Работает на iPhone (как установленное PWA-приложение) и в браузере — один код.

## 1. Ключевые решения

| Вопрос | Решение | Почему |
|---|---|---|
| Платформа | **PWA** на Next.js (TypeScript), «На экран Домой» в Safari; позже — **нативная оболочка Capacitor** для Apple Health и виджетов (§11) | Один код для iPhone и веба, камера и фото работают, без App Store на старте. Оболочка переиспользует тот же UI и API |
| Пользователи | **Открытая регистрация** (с 2026-10-01); многопользовательская схема с первого дня: `owner_id` во всех таблицах, проверка владельца в каждом запросе | Других людей добавили регистрацией и лимитами, без миграции данных |
| Бэкенд | Next.js route handlers (серверная часть того же проекта), Node в Docker | Ключ к LLM не должен попадать в браузер; один контейнер |
| БД | Postgres 17 в Docker на нашем VPS + Drizzle ORM | Синхронизация телефон ↔ веб, SQL для недельных агрегатов, данные у нас |
| Авторизация | Better Auth (библиотека внутри приложения): passkey (Face ID) + вход и регистрация по ссылке на email; лимиты писем на адрес и на сутки | Без внешнего сервиса; сессии в нашей БД; поддерживает Bearer-токены для нативного приложения |
| Файлы (фото еды) | Папка-том Docker на VPS, отдаётся только через API с проверкой владельца | Фото мало, S3 не нужен; бэкапится вместе с БД |
| ИИ | **Gemini API** (Google), бесплатный уровень: Flash-модели для фото и разбора текста, ответ строго по JSON-схеме | Подписку Claude нельзя использовать из своего приложения (только Claude Code/claude.ai); ключ Claude API — платный. Бесплатная квота Gemini — на проект Google; у calo свой ключ из Google AI Studio. Чужие аккаунты ограничены общим дневным лимитом (`AI_GLOBAL_DAILY_LIMIT`), на владельца он не действует |
| Хостинг | **Наш VPS**: Docker Compose (app + postgres) за Caddy/nginx с HTTPS Let's Encrypt на поддомене | Без сторонних аккаунтов и лимитов; HTTPS обязателен для PWA и камеры |

**Главный принцип: ИИ не придумывает цифры КБЖУ.** ИИ только превращает фото или
свободный текст в список `{продукт, граммы}`. Нутриенты всегда берутся из базы
продуктов и считаются детерминированно. Если продукта нет в базе, ИИ может дать
оценку, но она помечается как «оценка» и её видно в интерфейсе.

## 3. Модули (домен)

Вся логика расчётов — чистые TypeScript-функции в `src/domain/`, без зависимости
от БД и UI. Их легко тестировать.

- **nutrients** — вектор нутриентов и операции над ним (`add`, `scale(grams)` и
  обратное к нему `per100gOf(portion, grams)` — снимок записи на 100 г: правка
  граммов на сервере и в листе правки, «сохранить как блюдо»).
  Ключи: `kcal, protein, fat, carbs, fiber, sugar, vitA, vitC, vitD, vitE, vitK,
  b1, b2, b6, b9, b12, calcium, iron, magnesium, potassium, sodium, zinc,
  selenium, omega3`. Отсутствующее значение = `null` (не 0), чтобы отличать
  «нет данных» от «ноль».
- **norms** — дневные нормы из профиля и цели (см. §4а): калории по
  Миффлину — Сан Жеору × коэффициент активности ± поправка цели; белок г/кг веса;
  витамины и минералы по МР 2.3.1.0253-21 (российские нормы) с учётом пола и
  возраста. «Коридор нормы» по калориям — ±10%. Функция чистая:
  `computeNorms(profile, goal, weight) → Norms`, поэтому нормы пересчитываются
  при любой смене веса или цели.
- **recipe** — расчёт составного блюда: сумма ингредиентов, выход готового
  блюда (сухая паста 100 г → ~250 г готовой), нутриенты на 100 г и на порцию.
- **matcher** — сопоставление строки «сливки 20%» с записью в базе продуктов:
  полнотекстовый поиск + триграммы (`pg_trgm`) + алиасы; при неоднозначности
  отдаёт топ-3 кандидата для выбора пользователем.
- **meals** — приёмы пищи дня (§4б): куда встаёт новый приём по своему списку
  (`placeNewMeal`), приём по умолчанию (`defaultMealTarget`), подписи повторов
  («Перекус · 2»), названия и вид приёма.
- **aggregates** — сумма за день, среднее за неделю по дням с записями,
  сравнение с прошлой и позапрошлой неделей.
- **rules** — движок рекомендаций (см. раздел 6).

## 4. Модель данных

```sql
-- Справочник продуктов (общий + пользовательские)
foods (
  id, name_ru, aliases text[], brand,
  source        -- 'usda' | 'off' | 'manual' | 'ai_estimate'
  source_ref,   -- id в исходной базе / штрихкод
  nutrients_per_100g jsonb,
  default_portion_g, portion_label,   -- «1 яйцо = 55 г»
  owner_id null  -- null = общий справочник
)

-- Мои блюда: шаблоны и рецепты
recipes (
  id, owner_id, name, kind,   -- 'template' (фикс. КБЖУ) | 'composite'
  total_weight_g,             -- вес готового блюда
  nutrients_per_100g jsonb,   -- кэш расчёта
  default_portion_g, use_count, last_used_at
)
recipe_ingredients (recipe_id, food_id, grams, raw_text)

-- Дневник: приёмы пищи дня (§4б) и записи в них
day_meals (
  id, owner_id,
  date,                           -- местный день пользователя
  name,                           -- «Завтрак», «Перекус», «Второй завтрак»… — любое название
  position                        -- порядок в дне (дробный: вставка между соседями)
)                                 -- пустых приёмов не бывает
entries (
  id, owner_id, eaten_at,
  meal_id,                        -- приём дня (day_meals); местный день eaten_at = его date
  meal,                           -- вид 'breakfast'|'lunch'|'dinner'|'snack' — для «Моих блюд»
  input_method,                   -- 'template'|'recipe'|'product'|'photo'
  food_id null, recipe_id null,
  grams,
  nutrients jsonb,     -- СНИМОК на момент записи: правка продукта не меняет историю
  photo_path null, ai_confidence null, note
)

profiles (owner_id, sex, birth_year, height_cm, activity, timezone,
         meal_plan text[],        -- свой порядок приёмов, по умолчанию {Завтрак,Обед,Перекус,Ужин}
         show_meal_times,         -- показывать время приёмов (по умолчанию — нет)
         onboarded_at)
goals (owner_id, kind,           -- 'lose' | 'maintain' | 'gain'
       rate_kg_per_week,         -- 0.25 | 0.5 | 0.75 для lose/gain
       target_weight_kg null,
       valid_from)               -- история: смена цели = новая строка
weight_log (owner_id, measured_at, weight_kg,
            source)              -- 'manual' | 'apple_health'
norms_override (owner_id, nutrient, value)   -- ручная правка любой нормы

weekly_reports (owner_id, week_start,
                norms jsonb,     -- СНИМОК норм, действовавших на этой неделе
                payload jsonb, created_at)
```

Вес и цель хранятся как история, а не одно поле: смена цели в середине месяца не
переписывает оценку прошлых недель, а график веса появляется бесплатно. Текущий
вес — последняя запись `weight_log`, текущая цель — последняя строка `goals`.

## 4а. Онбординг и цель

Первый запуск — 4 коротких экрана в стиле листа со скриншота:

1. **Цель**: снизить вес / удержать / набрать; для снижения и набора — темп
   (спокойно 0,25 · умеренно 0,5 · быстро 0,75 кг/нед) и необязательный целевой вес.
2. **О себе**: пол, год рождения.
3. **Тело**: рост и текущий вес (первая запись в `weight_log`).
4. **Активность**: 5 уровней с понятными примерами («сидячая работа, без спорта»…).

Финал — экран «Ваша норма 2 450 ккал · белок 130 г» с кнопкой «Начать».
Всё меняется потом во вкладке **Профиль**; нормы пересчитываются сразу.

Расчёт калорий по цели:
- TDEE = BMR (Миффлин — Сан Жеор) × коэффициент активности (1,2…1,9);
- снизить: TDEE − темп × 7700 / 7, но не ниже max(BMR × 1,1; 1200 ккал для женщин /
  1500 для мужчин) — если темп упирается в порог, приложение говорит об этом;
- удержать: TDEE; набрать: TDEE + темп × 7700 / 7 (в пределах +15%);
- белок: снижение 1,8 г/кг, удержание 1,4 г/кг, набор 1,8 г/кг;
- жиры ≥ 0,8 г/кг, углеводы — остаток.

Раз в неделю (в недельном разборе) приложение просит обновить вес, если последняя
запись старше 7 дней. Позже вес будет приходить из Apple Health автоматически.

## 4б. Приёмы пищи

День — **упорядоченный список приёмов**: сколько угодно приёмов с любыми
названиями, перекусов — сколько угодно. Порядок важнее времени: по умолчанию
время приёмов нигде не показывается.

- **Свой список приёмов** — `profiles.meal_plan` (Профиль → «Приёмы пищи»):
  1–12 названий по порядку, повторы можно (два «Перекуса» — два места в дне); у
  нового пользователя «Завтрак · Обед · Перекус · Ужин». Правка списка не трогает
  уже заполненные дни. Там же переключатель «Показывать время приёмов пищи»
  (`show_meal_times`, по умолчанию выключен). `GET / PUT /api/profile/meals
  { plan?, showTimes? }` (до онбординга — 409); страницы берут настройки из `loadUser`
  («Добавить» — только их, `getMealSettings`).
- **Приём дня** — строка `day_meals` (название и `position`); запись принадлежит
  приёму (`entries.meal_id`), местный день записи — день приёма (по нему же
  считают полоса недели, недельный разбор и CSV). Пустых приёмов не бывает:
  удаление или перенос последней записи удаляет и приём.
- **Куда встаёт новый приём** — `domain/meals.ts placeNewMeal`: по своему списку.
  k-й приём дня с названием X — k-е вхождение X в списке; новый встаёт перед
  первым приёмом, который в списке дальше (позиция — середина между соседями),
  иначе в конец; названия не из списка — в конец. Внутри дня приём можно
  передвинуть выше / ниже.
- **Приём по умолчанию** — `defaultMealTarget`, одно правило для сервера (запись
  без приёма: виджет, старые клиенты) и листа порции: приём из ссылки (по id или
  названию) → сегодня — приём, в который добавляли за последние 90 минут →
  следующий незанятый по списку после последнего занятого → в пустой день —
  приём списка по часу «сейчас» (иначе первый) → по часу / последний приём дня.
- **Время** вторично: у записи есть `eaten_at` (для Здоровья и сумм по дням),
  время приёма — время его первой записи. Без явного времени: сегодня — «сейчас»,
  в прошлый день — время первой записи приёма, иначе типичное (8:30 / 13:30 /
  16:30 / 19:30; своё название — по виду, в полдень 13:30). С включённым показом
  времени его можно выбрать для нового приёма и поменять всему приёму.
- API:
  - `loadDay` (дневник и `GET /api/entries?date=`) → `{ date, entries, totals,
    meals }`; `meals` — приёмы дня по порядку `{ id, name, position, time, lastAt,
    entries, totals }`.
  - `POST /api/entries { foodId|recipeId, grams, date?, mealId? | mealName?
    (+newMeal), time?, eatenAt?, meal? }`: `mealId` — этот приём (другого дня —
    400; не нашёлся — по `mealName`, без него — 404: приём удалили, пока запись
    ждала в офлайн-очереди, — она не теряется); `mealName` — приём дня с этим названием (из нескольких —
    последний), иначе новый по списку; `newMeal` — всегда новый (второй
    «Перекус»); без приёма — приём по умолчанию. Будущих дней нет: `date` позже
    сегодня (в поясе профиля) — сегодня, а не 400, иначе офлайн-очередь выбросила
    бы запись телефона, чьи часы впереди (с `mealId` такая дата отбрасывается —
    день берёт приём); несуществующая дата («2026-02-30») — 400; `eatenAt` — в пределах двух суток и не
    в будущем дне (`lib/diary-date.ts newEntryTiming`). Старые тела работают:
    офлайн-очередь `{…, meal, eatenAt}` и виджет `{ recipeId, grams, eatenAt }`.
  - `PATCH /api/entries/:id { grams?, mealId? | mealName? (+newMeal, time?) }` —
    граммы и перенос в приём того же дня: в приём с записями — на его время, в
    новый — время прежнее (или `time`); `DELETE /api/entries/:id`. Опустевший
    приём удаляется.
  - `PATCH /api/meals/:id { name?, time?, move?: "up"|"down" }` — переименовать
    (вид записей пересчитывается), поставить всем записям время, поменяться
    местами с соседом → `{ meals }` дня по порядку. `DELETE /api/meals/:id` →
    `{ deletedEntryIds }` — клиент удаляет эти записи и из Здоровья.
  - Запись, правка и удаление идут в транзакции под блокировкой владельца: две
    отправки подряд не заводят два одинаковых приёма.
- Клиент: выбор приёма — `ui/MealPicker`: кнопки приёмов дня по порядку
  («Завтрак», «Перекус · 2»; с показом времени — «Обед 13:05») и «+ новый» —
  название из своего списка или своё; поле времени — только при включённом
  показе; в строке заголовка — куда новый приём встанет. Логика —
  `lib/meal-choice.ts` (`toDayMeals`, `defaultMealChoice`, `mealChoiceBody`:
  начатый приём — `{ mealId, mealName }`, новый — `{ mealName, newMeal?, time? }`). Разбор
  текста заводит новый приём один раз: первая позиция — по названию, остальные —
  по `mealId` из её ответа. Все добавления с клиента идут через `postEntry`
  (`lib/offline.ts`, офлайн-очередь). Название приёма — до 40 знаков по кодовым
  точкам (`normalizeMealName`; поля ввода режут так же — `clampMealName`, эмодзи
  не съедают лимит вдвое); в API — общее поле `lib/meal-schema.ts MealNameField`.
- Вид приёма (`entries.meal`) пересчитывается из названия и часа (`mealKindOf`):
  по нему «Мои блюда» сортируются под приём (`/api/recipes?meal=|?mealName=`);
  старые ссылки `/add?meal=lunch` понимаются как «Обед».
- Миграция `0005_day_meals`: по приёму на (владелец, местный день, вид приёма
  записи — «Завтрак» / «Обед» / «Перекус» / «Ужин»), порядок — по первой записи;
  местный день — в поясе профиля (неизвестный пояс или нет профиля — Москва).
  Заменила прежние 0005 + 0006: `when` в журнале — как у прежней 0006, поэтому
  базы, где они уже применены, её пропускают.

## 5. Четыре способа добавить еду

Все четыре сходятся в одну точку — **экран подтверждения**: список позиций с
граммами, КБЖУ и кнопкой «Добавить». Пользователь всегда может поправить граммы
или заменить продукт перед сохранением.

1. **Шаблон** («Мои блюда»). Список отсортирован по частоте и времени суток
   (утром наверху завтраки). Одно касание → порция по умолчанию, долгое → выбор
   граммов.
2. **Ручной ввод с расчётом.** Строка «паста: 50 г сливок 20%, 50 г пармезана,
   100 г сухой пасты Rummo» → `/api/parse/text` → ИИ возвращает
   `[{name, grams, state: 'raw'|'cooked'}]` → matcher → ингредиенты → расчёт.
   Кнопка «Сохранить как блюдо» превращает это в шаблон.
3. **Известный продукт.** Поиск по базе с автодополнением: «яйцо 2 шт», «кефир
   250». Короткий ввод парсится регуляркой без ИИ (число + единица), единицы
   «шт/ложка/стакан» переводятся через `default_portion_g`.
4. **Фото.** Снимок сжимается на клиенте (≤1568 px по длинной стороне, JPEG) →
   `/api/parse/photo` → Gemini (vision) возвращает позиции с оценкой граммов и
   уверенностью → matcher → экран подтверждения. Позиции с низкой уверенностью
   подсвечиваются. Фото сохраняется к записи.

Ответ ИИ всегда в строгом JSON через tool use (схема задаётся в коде), с
валидацией через Zod. Ошибка разбора → понятное сообщение и переход в ручной ввод.

## 6. Недельный разбор и рекомендации (экран со скриншота)

Считается детерминированно из записей; тексты — из шаблонов фраз, поэтому цифры
в тексте всегда совпадают с данными.

**Шапка**: среднее ккал в день по дням с записями, норма, «N из 7 дней».

**Что получилось** (зелёные галочки) — правила, которые сработали положительно:
- дневник вели ≥ 6 дней из 7;
- K дней из 7 в коридоре нормы (±10%);
- белок добран (≥ 90% нормы) в K днях;
- разрыв с нормой сократился на X% против позапрошлой недели.

**На что посмотреть** (оранжевый) — отклонения:
- калорий на X% больше/меньше, чем на прошлой неделе (если |X| ≥ 5%);
- белок ниже нормы в большинстве дней;
- натрий выше нормы, клетчатка ниже и т. п.

**Чем добрать на этой неделе** (синий лист) — 3 нутриента с наибольшим
недобором (среднее < 70% нормы) + статичная таблица источников:
«Витамин K → зелень, капуста, брокколи», «Кальций → творог, сыр, кефир, кунжут».
Источники можно ранжировать по тому, что пользователь и так ест (из его
шаблонов), чтобы советы были реалистичными.

**Защита от ложных выводов**: если у заметной доли записей нет данных о
микронутриенте (например, продукты из Open Food Facts без витаминов), рекомендация
по нему не показывается, а внизу пишется «по витаминам данных мало».

Каждое правило — объект `{id, when(ctx), severity, render(ctx)}`; добавлять новые
правила просто, и каждое покрыто тестом.

Разбор формируется в понедельник при первом открытии и кэшируется в
`weekly_reports`. Первый запуск после окончания недели (в ней ≥ 3 дней с записями)
открывает его сам — листом с кнопкой «Понятно»; открывшийся разбор отмечается
просмотренным ещё на сервере, до показа (`week/page.tsx`), — уйти можно и
вкладкой «Дневник» (`/`), она не вернёт в разбор. В остальное время он — на
вкладке «Неделя».

## 7. База продуктов

Слоями, по приоритету:
1. **Мои продукты и блюда** — всё, что пользователь создал или поправил.
2. **Базовый справочник ~1500 продуктов** — USDA FoodData Central (Foundation +
   SR Legacy: полный набор витаминов и минералов, открытая лицензия) с русскими
   названиями и алиасами. Перевод и алиасы генерируются один раз скриптом и
   проверяются вручную для топ-300 продуктов.
3. **Open Food Facts** — брендовые продукты (Rummo, творог конкретной марки),
   поиск по названию и штрихкоду. Обычно только КБЖУ, без витаминов.
   Штрихкод (`GET /api/foods/barcode/:code`) у сканера — сначала свой продукт с
   ним, затем OFF; товар, выбранный из результатов поиска OFF, запрашивается с
   `?source=off` — свой продукт с тем же штрихкодом его не подменяет.
4. **Оценка ИИ** — последний вариант, запись помечена `source='ai_estimate'`.

Дизайн-токены сняты со скриншота:

|---|---|

| `--ink-2` | `#5E6072` вторичный текст |

| радиусы | лист 32 px, кнопка 20 px |
| шрифты | крупные цифры — широкий гротеск (Unbounded 800); текст — Manrope; подписи — JetBrains Mono |

Навигация — панель вкладок внизу (`ui/TabBar`): **Дневник · Неделя · Блюда ·
Профиль**. Её нет на «Добавить», в онбординге и редакторе блюда (там своя кнопка
внизу) и пока открыта клавиатура. Страницы с вкладками отступают снизу на
`--tabbar-space` (утилита `pb-tabbar`), липкие кнопки стоят над панелью.

Экраны:
- **Дневник** («Лента», `/?d=2026-09-30`; будущая дата — сегодня) — полоса недели
  пн–вс (выбранный день, сегодня, будущие бледные; точка — калории дня в коридоре
  нормы / выше / ниже, суммы дней — одним запросом, `db/entries.ts kcalByDay`),
  сводка: крупное число ккал, «из 2 450 · осталось 810», полоса, чипы
  «Б 96/130 · Ж 52/80 · У 180/260» (ведут в нутриенты дня). Ниже — приёмы дня по
  порядку (§4б): название (повтор — «Перекус · 2») и ккал, «+» — добавить в этот
  приём, под ними записи; время приёма — колонкой слева, только если его показ
  включён в Профиле. Нажатие на приём — лист: «Выше / Ниже», название (из своего
  списка или своё) и, при показе времени, время всего приёма, «+ Добавить в этот
  приём», «сохранить как блюдо», «Удалить приём»; на запись — граммы, перенос в
  другой приём, удаление. Пустой день — кнопки «+ Завтрак»… по своему списку.
  Над вкладками — строка «Что съели? «творог 180, кофе»»: текст уходит на
  «Добавить» во вкладку «Текст» и разбирается сразу, штрихкод сканируется прямо здесь.
- **Добавить** (`/add`) — вкладки Продукт · Текст · Мои блюда (фото — этап 7).
  Ссылки: `?d=` — день (будущий — сегодня), `&meal=<id приёма дня>` — в этот
  приём («+» у приёма), `&meal=Обед` — в приём дня с этим названием или новый (кнопки пустого дня;
  старое `&meal=lunch` тоже), `&text=` — разобрать текст из строки дневника,
  `&tab=food|text|recipes`. После записи — назад в дневник `/?d=…`.
- **Порция** — лист снизу: граммы кнопками «−/+ 10» (удержание — быстрее),
  ползунком и быстрыми порциями, без клавиатуры (`ui/GramsInput`); КБЖУ на лету;
  выбор приёма (`ui/MealPicker`).
- **Подтверждение разбора** — список позиций с граммами (лист граммов вместо
  поля ввода), выбор приёма, итог, «Добавить».
- **Неделя** — разбор как на скриншоте + график ккал по дням.
- **Нутриенты** — % нормы по каждому витамину и минералу за день/неделю.
- **Блюда** — шаблоны и рецепты, редактор рецепта.
- **Онбординг** — 4 шага: цель, о себе, рост и вес, активность (§4а).
- **Профиль** — цель и темп, параметры тела, вес (с графиком), ручная правка норм;
  «Приёмы пищи» — свой порядок приёмов (переименовать нажатием, ↑ / ↓, убрать,
  «+ Добавить приём») и переключатель показа их времени; каждая правка
  сохраняется сразу (§4б).

iPhone: экранная клавиатура ложится поверх страницы, а не сжимает её. Листы
снизу (`ui/BottomSheet`), строка ввода дневника и сканер поднимаются над ней
(`ui/useKeyboardInset`), панель вкладок прячется. Поля ввода — не мельче 16 px,
иначе Safari увеличивает страницу при фокусе и она уезжает вбок. `maximumScale`
в viewport не ставим: WKWebView приложения его уважает и отключил бы щипок-зум.

## 10. Приватность и стоимость

- Бесплатный уровень Gemini: Google может использовать запросы для улучшения
  продуктов, их могут читать разметчики (обезличенно). Для пользователей из
  ЕЭЗ, Швейцарии и Великобритании действуют условия платного уровня — без этого.
  В ИИ уходят только фото еды и текст рецепта, без имени и email.
- Квота бесплатного уровня — на проект Google: у calo свой ключ из Google AI
  Studio, с egormath квота не делится.

- Все данные закрыты авторизацией; изоляция — проверка владельца в каждом
  запросе: функции слоя `db/` принимают `ownerId` и фильтруют по `owner_id`.
  Postgres RLS нет.
- Бэкап: ночной `pg_dump` + архив папки фото, копия за пределы VPS, хранение 14 дней.
- Лимиты запросов к ИИ: на пользователя в день (`AI_DAILY_LIMIT`,
  `ai_usage(owner_id, day, requests)`) и общий дневной на всех, кроме владельцев
  (`AI_GLOBAL_DAILY_LIMIT`, счётчик в `app_meta`, день по UTC) — чтобы чужие
  аккаунты не съели квоту ключа.
- Фото отправляются в Gemini API только при выборе способа «Фото».
- Стоимость ИИ для одного пользователя — копейки в день: ~5 фото и ~5 разборов
  текста. Дневные лимиты выше — страховка на случай ошибки.

## 11. Задел под нативное приложение (Apple Health и виджеты)

Чтобы потом не переписывать, уже сейчас соблюдаем правила:

- **UI — клиентские компоненты, которые ходят только в `/api/*`.** Никаких server
  actions и серверного рендеринга данных. Тогда фронтенд собирается статикой
  (`next build` + static export клиентской части) и кладётся внутрь Capacitor,
  а API остаётся на VPS.
- **Авторизация по токену**: API принимает `Authorization: Bearer <session token>`,
  а не только cookie — так же будут ходить нативное приложение и виджет.
- **Сводка дня — отдельный компактный эндпоинт** `/api/summary/day`
  (`kcal, norm, protein, proteinNorm, updatedAt`) — ровно то, что нужно виджету.
- **Источник записи** (`weight_log.source`, `entries.input_method`) заложен, чтобы
  данные из Apple Health не дублировались с ручными.

Что добавится в нативной оболочке:

| Функция | Как |
|---|---|
| Apple Health — запись | После сохранения приёма пищи пишем `dietaryEnergyConsumed`, белки, жиры, углеводы, клетчатку, витамины (HealthKit-плагин Capacitor). Храним `healthkit_uuid` в `entries`, чтобы удаление в дневнике удаляло и в Health |
| Apple Health — чтение | Вес → `weight_log` (source=`apple_health`); активные калории → опционально уточняют TDEE |
| Виджет | Swift-расширение WidgetKit: кольцо «1 830 / 2 450 ккал» и белок. Данные — из App Group, куда приложение пишет сводку после каждого изменения; раз в 30 мин виджет сам обновляется через `/api/summary/day` |
| Быстрое добавление | Интерактивный виджет / App Intent «Добавить моё блюдо» → `POST /api/entries` |
